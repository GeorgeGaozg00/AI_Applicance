# v0.1 兼容矩阵与适配决策

范围：当前 Kunpeng / Ubuntu 22.04 / 310P3 开发服务器；宿主驱动 25.3.rc1、CANN 8.5.0。认证状态以本次完整验收报告为准，不能推广到其他服务器。

| 运行组合 | 已观察结果 | 使用决定 |
| --- | --- | --- |
| vLLM Ascend v0.14.0rc1-310p + Qwen2.5-0.5B-Instruct | 接口和生命周期可用，长回答异常重复 | 拒绝作为本版基线 |
| vLLM Ascend v0.14.0rc1-310p + Qwen3-0.6B | 输出乱码，基础问答失败 | 拒绝作为本版基线 |
| vLLM Ascend v0.15.0rc1-310p + Qwen3-0.6B FP16 | 普通/流式问答、三轮长回答通过，完整重载回归单独记录 | 选定开发验证底座 |
| 宿主机 PyTorch NPU | 缺少 libhccl.so | 使用隔离容器，不改宿主驱动/CANN |
| 容器内 Transformers NPU + Qwen2.5 | 对照文本正常，首次对照耗时约3175秒 | 仅作诊断，未选为服务引擎 |
| GPUStack | 尚未完成设备分配、引擎启动和回收的真机闭环 | v0.1采用直接Docker适配器；后续调度集成单独验收 |
| Embedding / Rerank | 本版未做模型真机验收；固定镜像310P attention代码明确拒绝 pooling runner | 不复用当前文本模型认证；v0.3前验证CPU独立服务或其他兼容引擎 |

Embedding/Rerank 的初步探查：已检查固定 v0.15 镜像内 `vllm_ascend/_310p/attention/attention_mask.py`，其中 `runner_type='pooling'` 抛出 `NotImplementedError`。这属于当前引擎路径的阻断，不能据此断言该硬件无法运行所有嵌入或重排模型。后续需分别测试文本向量维度、批处理、相似度、重排分数和资源占用，测试通过前不列入可部署目录。上游[310P pooling问题记录](https://github.com/vllm-project/vllm-ascend/issues/6471)也反映了此限制。

GPUStack 官方[设备要求](https://docs.gpustack.ai/2.0/installation/requirements/)列有310P3，但设备被列为支持不能替代当前固定引擎、驱动、模型组合的实测。当前版本按迭代计划允许的直接容器适配器实现闭环。

## 模型能力限制

Qwen3-0.6B 禁用思考后，对“请只回答一个数字：1加1等于几？”输出“1”。v0.15 NPU服务与同权重、同模板的Transformers CPU FP32贪心对照均得到该错误答案，输入均为24 token。原始失败验收与CPU报告保留在服务器 `shared/reports/v0.1.0-v015/`。

因此，重载检查改用与重载前相同的首都问题，并严格比较普通和流式回答是否分别一致，避免混入不同题目带来的模型能力差异。该调整不表示算术题已经通过，也不构成模型通用准确率认证。长回答异常重复检查继续保留。

本版只验证逻辑设备0、单实例、单并发、512 token上下文、eager模式、FP16。设备2的早期试验出现无效设备ID；其他设备映射、多卡、大模型、量化和生产长稳均需后续独立验证。
